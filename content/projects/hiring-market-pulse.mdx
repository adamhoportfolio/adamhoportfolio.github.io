<h2 id="tldr">Overview</h2>

Hiring Market Pulse is a data product I built that tracks how tech startups are hiring, based on the job posts in Y Combinator’s monthly thread.

It covers over 11,500 listings, alongside job-openings data from the Bureau of Labor Statistics. Every day it pulls in the latest posts and refreshes [the dashboard](https://hiring-market-pulse.streamlit.app/).

| Area | Tools |
|---|---|
| **Pipeline** | `Python` · `httpx` · `pydantic` · `pandas` · `Parquet` |
| **Warehouse** | Databricks (Unity Catalog, Delta) · `SQL` |
| **Modeling** | `dbt` · 52 data tests · mutation testing · accuracy audit |
| **CI/CD** | GitHub Actions · branch protection · gated publishing |
| **App & tests** | `Streamlit` · `Plotly` · `Playwright` · `pytest` |
| **Analysis** | `Jupyter` · `DuckDB` |
| **AI-assisted** | Claude Code |

Under the hood, it's an end-to-end pipeline. `Python` pulls data from two APIs and validates it with `pydantic` data contracts, then loads it into Databricks.

From there, `dbt` models it using `SQL` into analysis-ready tables, with 52 data quality tests that are themselves mutation-tested.

All of this runs on GitHub Actions for CI/CD, where changes can’t merge and data can’t be published unless all tests have passed. The dashboard is built in `Streamlit` as a web app that is automatically tested with `Playwright`.

<h2 id="pipeline">1 · Data pipeline</h2>

The pipeline is written in `Python` and runs once a day as a batch job.

It starts by calling two public APIs. One is the Algolia search API, which sits in front of YC’s Hacker News forum. The other is the BLS API for a survey called JOLTS, which is an official count of job openings. The requests go through `httpx`. If a service is busy or briefly down, the pipeline waits and tries again a few times before giving up.

```python
class RawPost(_Strict):
    post_id: int
    thread_id: int
    thread_month: date
    posted_at: datetime
    text_html: str = Field(min_length=1)

    @field_validator("posted_at")
    @classmethod
    def _not_in_future(cls, v: datetime) -> datetime:
        if v > datetime.now(UTC):
            raise ValueError("posted_at is in the future")
        return v
```

<p className="caption">Data contract for a raw post (<code>pydantic</code>), from <code>src/pulse/contracts.py</code></p>

Before anything is saved, each record is checked against a data contract written with `pydantic`. The contract spells out what a valid record looks like, so mistakes like missing IDs or negative numbers get caught. Records that *fail* go into a quarantine table along with the reason they were rejected.

Job posts are unstructured text, so the next step is pulling structure out of each one. A rules-based extractor, using `regex`, reads each post. It works out whether the job is remote, hybrid or onsite, plus the salary range, role, seniority, location and tech stack.

All of that gets written into `Parquet` files using `pandas`.

![Databricks Catalog Explorer: the pulse_raw schema with its five raw tables and the landing volume](/images/databricks-catalog.png)

<p className="caption">Databricks Catalog Explorer: the raw Delta tables and the <code>landing</code> volume in Unity Catalog</p>

Those files are uploaded to a volume in Databricks and loaded into Delta tables in Unity Catalog. Each load replaces the table instead of adding to it, so running the same day twice won't create duplicates.

<summary>More detail</summary>

If the source ever adds or renames a field, the data that doesn't fit is kept in its own column rather than dropped, which makes that kind of change easy to spot.

</details>

Once the raw data is in the warehouse, I model it with `dbt`, using `SQL`.

The first layer is staging, where the raw tables get cleaned up and standardized.

These evolve into data marts. Data marts are tables that the dashboard and analysis actually read from. There's one with a row for every post and one that rolls everything up by month. Others break the data down by role, technology and salary, and the last one lines Hacker News up against the government numbers.

Every model and column has a description. `dbt` turns all of it into this docs site, so anyone can look up what a field means and where it comes from.

```text
Finished running 11 table models, 52 data tests in 0 hours 0 minutes and 51.77 seconds (51.77s).
Completed with 1 warning:
Done. PASS=62 WARN=1 ERROR=0 SKIP=0 NO-OP=0 REUSED=0 TOTAL=63
```

<p className="caption"><code>dbt build</code> output from a daily refresh run (52 tests + 11 models = 63 nodes)</p>

There are 52 data tests that run on every build, using `dbt`'s built-in tests and the `dbt_utils` package. They check that IDs are unique and every post belongs to a real thread. They also check for invalid and missing values.

```text
CAUGHT  duplicate post              -> source_unique_raw_hn_posts_post_id [fail]
CAUGHT  inverted salary range       -> salary_min_not_above_max [fail]
CAUGHT  gap in JOLTS series         -> assert_no_missing_jolts_months [fail]
CAUGHT  missing month of threads    -> assert_no_missing_hn_months [fail]
CAUGHT  quarantine spike            -> assert_quarantine_rate_below_5pct [fail]
...
11/11 mutations caught
```

<p className="caption">Mutation check output from CI (5 of the 11 corruptions shown). More in the <a href="https://github.com/wacsvn/hiring-market-pulse/blob/main/docs/case-studies/tests-that-couldnt-fail.md">case study</a>.</p>

These tests are also *themselves* tested. A mutation check copies the data, breaks it in eleven different ways and confirms the right test fails each time. This is how a real gap was found and closed: a month with no posts at all could slip past the check that was supposed to catch missing months.

To test whether the extractor read a post correctly, I put together 50 sample posts with answers drafted by AI and spot-checked by hand (20 verified, 99% agreement), and scored the extractor against them with `pytest`.

<details>
<summary>More detail</summary>

They also check that values come from the expected list, that a minimum salary is never above the maximum, that no months are missing and that the data is fresh.

![dbt docs page for the warn-level divergence test](/images/hmp/dbt-warn-test.png)

<p className="caption">The one warn-level test: HN and official data diverging</p>

One of them is deliberately a warning rather than a failure. It flags months where Hacker News and the official data move in very different directions. That's worth a person taking a look, but it doesn't necessarily mean anything is wrong.

![Dashboard Data quality tab: extractor accuracy table](/images/hmp/dash-accuracy.png)

<p className="caption">Extractor accuracy, as shown on the dashboard's Data quality tab</p>

Work arrangement and salary detection both came out at 98 percent.

| Field | Accuracy |
|---|---|
| Work mode (remote / hybrid / onsite / unknown) | 98% |
| Salary found when present, absent when not | 98% |
| Salary values correct (of posts that state one) | 93% |
| Role families exactly right | 70% |
| Seniority | 91% |

The audit also caught a definition problem that was undercounting remote jobs by about five points. After I fixed it, the overall trend held, which was reassuring. That score is now a baseline, and if a future change makes the extractor less accurate, the build fails.

The fixes it prompted took work-mode accuracy from 91% to 98% and seniority from 70% to 91%.

</details>

Every change goes through a pull request, and the main branch is protected, so nothing can merge until the checks pass. They cover linting with `ruff`, type checking with `mypy` and 90 unit tests using `pytest` and `Hypothesis`. There's also a full `dbt` build with every data test, against a Databricks schema set aside for CI, and browser tests for the dashboard ([shown below](#dashboard)).

The lint and type checks also run on my machine through `pre-commit` hooks before I commit, to avoid any CI surprises.

Publishing means uploading the finished marts as files to a GitHub Release. The dashboard reads from that release instead of querying Databricks directly. That keeps the app fast and free to run, and it means the dashboard only ever sees data that has already passed the tests.

If something fails, nothing gets published and the dashboard keeps showing the last good data. A GitHub issue opens automatically with the details.

Other workflows republish the `dbt` docs to GitHub Pages and check the live dashboard every few hours.

## Question

What do three years of startup hiring posts say about remote work, pay transparency, and in-demand skills? And how can a reader know the numbers are right?

## Findings (Nov 2023 to Sep 2026)

The data covers companies that post in Hacker News' monthly "Who is hiring?" thread: mostly startups and engineering teams in U.S. tech hubs, so read the findings as a view of that corner of the market.

- Posts listing a salary rose from 13% to 31%
- Remote-friendly posts fell from 67% to 55%; onsite-only rose from 15% to 25%
- LLM/GenAI mentions doubled, from 8% to 16% of posts
- HN post volume fell 6% while official Information-sector openings fell 35%, so HN is not a stand-in for the broader market
